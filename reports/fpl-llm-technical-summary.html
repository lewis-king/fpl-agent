01 / Where we are

The pipeline works. Model promotion remains evidence-led.

Multiple LoRA candidates through v9 were trained and compared with the untouched base model. The final result is deliberately nuanced: v9 learned the four application tool routes and improved screenshot extraction, but the base model with the same system policy and typed tools remains the safer chat backbone. Further LoRA work is parked.

Use specialised learning where it helps; retain deterministic authority where mistakes matter.

Fine-tuning improved FPL-specific behaviours, but no adapter improved every text contract at once. That is not a failed experiment. It gives us measured deployment boundaries instead of assuming a lower training loss means a better product.

Why this is a good idea

01
Small, local and controllable

A 4B model runs and fine-tunes on one RTX 5090. Iterations take tens of minutes, not days, and private app data does not need to leave the machine.

02
Stable behaviour is separated from changing facts

The adapter learns FPL vocabulary, dialogue patterns and when to use tools. Live prices, injuries, ownership and fixtures are fetched at answer time instead of fossilised into weights.

03
Multimodality is preserved

Qwen remains able to read team screenshots directly. OCR can supply supporting evidence, but pitch structure, badges and bench semantics are handled by the vision-language model.

04
The model never becomes the rules engine

Entity IDs, squad legality, formation, budget constraints and optimisation remain deterministic. The model interprets, routes and explains; code validates and decides.

03 / Training mechanics

LoRA changes a small set of learned directions.

This is a Python training pipeline built with Unsloth, TRL, PEFT and Transformers—not a desktop application. The original Qwen weights stay frozen while compact low-rank matrices learn the FPL-specific adjustment.

Load the multimodal base

unsloth/Qwen3.5-4B is loaded in BF16. We deliberately avoided 4-bit QLoRA for this model family.

Attach rank-16 LoRA adapters

Trainable low-rank matrices are added to language attention and MLP modules. The large base weights stay frozen.

Freeze the vision encoder

Existing visual capability is retained. Screenshot examples train the language side to interpret visual embeddings into our extraction contract.

Mask prompts and tool evidence

Loss is applied only to assistant responses and tool calls. System prompts, user text and tool results are context, not targets to memorise.

Train one controlled epoch

Batch 2 with eight-step gradient accumulation gives an effective batch of 16. A four-hour wall-clock callback protects the local run.

Apply the learned delta

At inference, each targeted weight behaves as W′ = W + (α/r)BA. With rank 16 and alpha 16, the LoRA scale is 1.0; W stays frozen while the learned A and B matrices alter the forward pass.

Select by locked evaluation

Adapters are compared against the same prompts, tool schemas and screenshots. Training loss is recorded, never used as the promotion decision.

04 / Runtime architecture

Weights, evidence and code each have one job.

The core design avoids asking a language model to be a database or optimiser. It combines natural interaction with current evidence and exact application logic.

Model weights

Stable FPL behaviour

The base supplies general intelligence. An attached adapter can bias language, clarification, tool selection and screenshot output toward our examples.

  • Base language and vision capability
  • Optional FPL vocabulary adaptation
  • Learned tool-call habits
  • Visual extraction behaviour
Tools now / RAG next

Current evidence

Time-sensitive facts arrive at inference time with provenance and observation dates.

  • Prices, fixtures and availability
  • Manager state and transfers
  • Versioned rules and research
  • Decision-engine receipts
Deterministic code

Hard correctness

Anything with a strict invariant stays in schemas, resolvers, validators and optimisers.

  • Player entity IDs
  • Budget and club limits
  • Formation and slot uniqueness
  • Captain and transfer optimisation
KEY BOUNDARY

The model may propose and explain. It may not silently repair an illegal team, invent a player ID, treat old screenshot metadata as live state, or override the numeric decision engine.

05 / Fine-tune, prompt, RAG or tools?

These techniques solve different problems.

The strongest design is layered. Fine-tuning creates a reusable behavioural prior; the system prompt defines this session's contract; RAG supplies relevant documents; tools obtain exact changing state; deterministic code owns rules and maths.

Why not just make the prompt enormous?

A large context window is capacity, not free intelligence. Repeating dozens of examples on every request consumes input tokens, increases prefill latency, competes with the user's actual evidence and can make a small model less consistent as instructions pile up. Fine-tuning compresses recurring patterns into weights once. The prompt can then stay focused on current policy and the retrieved context can stay focused on the current question.

Versioned logic

Fine-tuning changes the prior—not the truth.

The LoRA makes certain outputs more likely before the current question is even seen. It does not guarantee correctness, create a database inside the model or remove the need for instructions. Facts learned into weights are difficult to date, cite or delete, so we deliberately avoid training current prices, injuries and weekly picks as permanent knowledge.

The practical win is behavioural compression: instead of carrying the same library of FPL examples in every prompt, the adapter stores a compact learned adjustment. That can reduce repeated context and teach patterns that prompting alone does not elicit reliably. Whether it actually improves this product is decided by locked evaluation, not enthusiasm or training loss.

Keep in weightsTerminology, conversational style, tool habits, extraction contracts.
Keep in promptIdentity, permissions, safety, active event and response policy.
Keep in RAGRules, methods and documents with dates and provenance.
Keep in toolsLive facts, manager state and versioned model outputs.
Keep in codeConstraints, validation, optimisation and final authority.
DESIGN RULE

Fine-tuning is not a substitute for a system prompt. The adapter supplies learned instincts; the system prompt supplies today's job, boundaries and context.
